# Initial Bootstrap Plan

## Goal

Bootstrap `legend-apps` as a monorepo with one reusable React Native app shell and multiple command-selected apps.

The first proof should include:

- A shared `shell` React Native app for `ios`, `android`, and `macos`.
- Expo prebuild support for generating `shell/ios` and `shell/android`.
- A manually maintained `react-native-macos` project in `shell/macos`.
- Two apps:
  - `apps/music`, rendering `Hello Music`.
  - `apps/markdown`, rendering `Hello Markdown`.
- One shared native package:
  - `packages/music-test`, containing a TurboModule plus a native UI component that renders `Music Test Native`.
- Root scripts that can run each app in development and build release outputs.
- Verification that `markdown` does not include or link `music-test`.

## Architecture

Use one native shell and select the active app per command invocation.

Do not check in a persistent `current app` source file. Instead, command scripts pass app and platform context through environment variables and generated build artifacts under `shell/.legend/generated/<app>/<platform>/`.

The shell source imports a stable virtual module:

```ts
import { App } from "@legend-apps/app";

export default App;
```

Metro resolves `@legend-apps/app` to exactly one app package based on the command environment:

```txt
LEGEND_APP=music
LEGEND_PLATFORM=macos
```

This keeps the JavaScript graph app-specific. The `music` bundle can include `packages/music-test`; the `markdown` bundle should not see it unless markdown imports it.

Native linking is also app-specific. Each app owns a manifest declaring its supported platforms and native dependencies. The run/build script reads that manifest, generates temporary config for the selected app/platform, and then invokes Expo, React Native, CocoaPods, Gradle, or Xcode commands with that generated context.

## App Manifests

Each app gets an `app.manifest.ts` used by all scripts.

Example `apps/music/app.manifest.ts`:

```ts
export default {
  id: "music",
  displayName: "Legend Music",
  platforms: ["macos", "ios", "android"],
  bundleIds: {
    ios: "so.legend.music",
    macos: "so.legend.music.macos",
  },
  androidPackage: "so.legend.music",
  nativeModules: {
    macos: ["@legend-apps/music-test"],
    ios: ["@legend-apps/music-test"],
    android: ["@legend-apps/music-test"],
  },
};
```

Example `apps/markdown/app.manifest.ts`:

```ts
export default {
  id: "markdown",
  displayName: "Legend Markdown",
  platforms: ["macos", "ios", "android"],
  bundleIds: {
    ios: "so.legend.markdown",
    macos: "so.legend.markdown.macos",
  },
  androidPackage: "so.legend.markdown",
  nativeModules: {
    macos: [],
    ios: [],
    android: [],
  },
};
```

The manifests are the source of truth for app-specific native dependencies. Root package dependencies may include all workspace packages, but autolinking must be filtered by the active manifest.

For the first implementation, avoid making `shell/package.json` depend directly on every app package. The selected app should be pulled into Metro through `@legend-apps/app`, while native packages should be included through explicit generated autolinking config. This reduces the chance that Expo or React Native autolinking discovers inactive app dependencies through normal package dependency traversal.

## Commands

Root scripts should support the workflow the user wants:

```sh
bun run music macos
bun run music ios
bun run music android

bun run markdown macos
bun run markdown ios
bun run markdown android
```

Release builds:

```sh
bun run music build macos
bun run music build ios
bun run music build android

bun run markdown build macos
bun run markdown build ios
bun run markdown build android
```

Batch helpers:

```sh
bun run dev:all
bun run build:all
bun run verify:all
```

`package.json` can implement app commands as argument-forwarding scripts:

```json
{
  "scripts": {
    "music": "bun scripts/run-app.ts music",
    "markdown": "bun scripts/run-app.ts markdown",
    "build": "bun scripts/build-app.ts",
    "verify": "bun scripts/verify-app.ts",
    "prebuild": "bun scripts/prebuild-app.ts",
    "dev:all": "bun scripts/run-app.ts --all --dev-check",
    "build:all": "bun scripts/build-app.ts --all",
    "verify:all": "bun scripts/verify-app.ts --all"
  }
}
```

The app command parser should treat these as equivalent:

```sh
bun run music macos
bun run music dev macos
bun run music build macos
```

When the app command receives `build`, it should delegate to `scripts/build-app.ts` rather than trying to run a development command. This keeps the user-facing command shape short while keeping development, prebuild, build, and verification logic separated internally.

## Script Responsibilities

### `scripts/run-app.ts`

Responsible for development runs.

Steps:

1. Parse app id and platform.
2. Load `apps/<app>/app.manifest.ts`.
3. Validate the platform is supported.
4. Generate app/platform config under `shell/.legend/generated/<app>/<platform>/`.
5. Ensure native project state exists:
   - For `ios` and `android`, run `expo prebuild --platform <platform>` when native directories are missing or when the generated native config changed.
   - For `macos`, verify `shell/macos` exists and has pods installed when needed.
6. Start the platform dev command with `LEGEND_APP` and `LEGEND_PLATFORM`.

Platform commands:

```sh
cd shell && LEGEND_APP=music LEGEND_PLATFORM=ios npx expo run:ios
cd shell && LEGEND_APP=music LEGEND_PLATFORM=android npx expo run:android
cd shell && LEGEND_APP=music LEGEND_PLATFORM=macos npx react-native run-macos
```

### `scripts/build-app.ts`

Responsible for release builds.

Steps:

1. Parse app id and platform.
2. Load manifest.
3. Generate app/platform config.
4. Run clean prebuild for `ios` or `android` if necessary.
5. Run platform release command.
6. Write output paths and build metadata to `shell/.legend/builds/<app>/<platform>/`.

Initial release commands:

```sh
cd shell && LEGEND_APP=music LEGEND_PLATFORM=ios npx expo run:ios --configuration Release
cd shell && LEGEND_APP=music LEGEND_PLATFORM=android npx expo run:android --variant release
cd shell && LEGEND_APP=music LEGEND_PLATFORM=macos npx react-native build-macos --mode Release
```

### `scripts/prebuild-app.ts`

Responsible for iOS/Android native generation.

Inputs:

```sh
bun scripts/prebuild-app.ts music ios
bun scripts/prebuild-app.ts markdown android --clean
```

Behavior:

1. Generate active app config.
2. Invoke Expo prebuild from `shell`.
3. Pass app identity through `app.config.ts`.
4. Keep generated native projects reproducible from manifests and config plugins.

### `scripts/verify-app.ts`

Responsible for proving app-specific inclusion and exclusion.

Required checks:

1. Resolve Metro graph for each app/platform.
2. Build or export release JS bundle for each app/platform.
3. Assert `music` includes `@legend-apps/music-test` in JS and native autolinking output.
4. Assert `markdown` excludes `@legend-apps/music-test` from:
   - Metro dependency graph.
   - Release JS bundle text.
   - Expo autolinking output for `ios` and `android`.
   - React Native config output for `macos`.
   - Native build files generated for the selected platform.

Example verification commands:

```sh
bun run verify music macos
bun run verify markdown macos
bun run verify markdown ios --excludes @legend-apps/music-test
bun run verify markdown android --excludes @legend-apps/music-test
```

This is doable. The strongest verification is a combination of autolinking output and bundle inspection:

- Autolinking output proves the native module is not linked.
- Bundle inspection proves markdown did not accidentally include the JS wrapper.
- Native build file inspection catches generated Podfile/Gradle/project references.

## Shell Implementation

The shell should stay minimal:

```ts
// shell/index.ts
import { registerRootComponent } from "expo";
import ShellApp from "./src/ShellApp";

registerRootComponent(ShellApp);
```

```tsx
// shell/src/ShellApp.tsx
import { App } from "@legend-apps/app";

export default function ShellApp() {
  return <App />;
}
```

`shell/metro.config.js`:

- Uses `@expo/metro-config`.
- Uses `@rnx-kit/metro-config` if needed for macOS compatibility.
- Requires `LEGEND_APP`.
- Resolves `@legend-apps/app` to `../apps/<app>/src`.
- Adds root, apps, and packages to `watchFolders`.
- Keeps platform extension support for `ios`, `android`, `macos`, `native`, and default extensions.
- Uses app-specific cache keys so switching from music to markdown cannot reuse stale module resolution.

`shell/app.config.ts`:

- Requires `LEGEND_APP`.
- Loads `apps/<app>/app.manifest.ts`.
- Sets Expo name, slug, bundle id, Android package, icons, splash, orientation, and new architecture.
- Applies shared config plugins.
- Applies app-specific config plugins from the manifest.

`shell/react-native.config.js`:

- Requires `LEGEND_APP` and `LEGEND_PLATFORM`.
- Loads the selected manifest.
- Includes only native modules listed for the selected app/platform.
- Sets unrelated local native modules to `platforms: { ios: null, android: null, macos: null }` or omits them from explicit dependency roots.
- For macOS, the CocoaPods/autolinking path may still use iOS-style React Native config data while the podspec advertises `:osx` support. The implementation should verify the exact `react-native-macos` CLI output before assuming a distinct `macos` platform key is enough.

## Native Package: `packages/music-test`

The package should provide:

- A TurboModule named `MusicTest`.
- A native UI component named `MusicTestView`.
- JS exports:

```ts
export { default as MusicTest } from "./NativeMusicTest";
export { default as MusicTestView } from "./MusicTestViewNativeComponent";
```

For the initial proof, the UI component only needs to render native text:

```txt
Music Test Native
```

Implementation notes:

- iOS and macOS can share Objective-C++/C++ codegen structure where practical, but AppKit/UIKit view classes should stay platform-specific.
- Android should use the New Architecture component path.
- Keep the module intentionally tiny so bootstrap complexity stays in the shell/config system, not native behavior.
- The `music` app should render the native view under `Hello Music`.
- The `markdown` app should not import `@legend-apps/music-test`.

## Native Linking Strategy

Use app manifests as the source of truth.

For Expo modules:

- Configure Expo autolinking `searchPaths` to know where workspace packages live.
- Use `exclude` for app/platform packages not listed in the active manifest.
- If a future local package is implemented as an Expo module, ensure the directory shape matches Expo Autolinking expectations or pass explicit options from the generated Podfile/Gradle config. The initial `music-test` package is planned as a React Native New Architecture module, so `react-native.config.js` is the primary linking control.

For React Native modules:

- Generate or compute `react-native.config.js` dependencies from the active manifest.
- For excluded modules, set the selected platform to `null` where needed.
- Prefer explicit dependency roots for selected local packages over broad monorepo scanning.
- Run `expo-modules-autolinking react-native-config --platform ios` and the Android equivalent during verification to inspect the actual dependency set produced for the active app.

Expected result:

- `music` autolinks `@legend-apps/music-test`.
- `markdown` does not autolink `@legend-apps/music-test`.

## iOS and Android Prebuild

Expo prebuild should be the source of truth for `shell/ios` and `shell/android`.

Initial policy:

- Treat `shell/ios` and `shell/android` as generated artifacts.
- Encode native changes through `shell/app.config.ts` and config plugins.
- Use `expo prebuild --clean` when native config changes materially.
- Keep generated native directories gitignored unless debugging proves we need to commit them.

Commands:

```sh
bun scripts/prebuild-app.ts music ios
bun scripts/prebuild-app.ts music android
bun scripts/prebuild-app.ts markdown ios
bun scripts/prebuild-app.ts markdown android
```

## macOS Project

Expo does not generate macOS native projects. Bootstrap `shell/macos` from a minimal `react-native-macos` app, using the reference project as the starting point.

The macOS project should:

- Use the shared shell JS entry.
- Bundle through Expo CLI-compatible entry resolution.
- Read generated app metadata for bundle id and display name.
- Build with `react-native run-macos` for dev.
- Build with `react-native build-macos --mode Release` for release.
- Use a podspec with macOS support for selected native packages, for example `s.platforms = { :ios => "...", :osx => "..." }`.

No manual Xcode workflow is required for the first pass.

## Verification Plan

### Basic Smoke Tests

Run each app in dev:

```sh
bun run music macos
bun run markdown macos
bun run music ios
bun run markdown ios
bun run music android
bun run markdown android
```

Expected UI:

- Music: `Hello Music`, plus `Music Test Native`.
- Markdown: `Hello Markdown`.

### Release Builds

Build all release targets:

```sh
bun run music build macos
bun run music build ios
bun run music build android
bun run markdown build macos
bun run markdown build ios
bun run markdown build android
```

Expected:

- All selected platform builds complete.
- Outputs are recorded under `shell/.legend/builds`.

### Exclusion Verification

For markdown:

```sh
bun run verify markdown macos --excludes @legend-apps/music-test
bun run verify markdown ios --excludes @legend-apps/music-test
bun run verify markdown android --excludes @legend-apps/music-test
```

The verifier should fail if any of these include `music-test`:

- Metro graph.
- Release JS bundle.
- Expo autolinking JSON.
- React Native config JSON.
- Pod project references.
- Gradle project references.
- macOS Xcode project references.

For music:

```sh
bun run verify music macos --includes @legend-apps/music-test
bun run verify music ios --includes @legend-apps/music-test
bun run verify music android --includes @legend-apps/music-test
```

The verifier should fail if the JS wrapper or native module is missing.

## Implementation Phases

### Phase 1: Monorepo Skeleton

Create:

- Root `package.json`.
- Root `tsconfig.json`.
- Root `.gitignore`.
- `apps/`, `packages/`, `scripts/`, and `shell/`.
- Workspace package naming convention:
  - `@legend-apps/app-music` if app packages need package names.
  - `@legend-apps/music-test` for shared packages.

Validation:

```sh
bun install
bun pm ls
```

### Phase 2: Shell App

Create the React Native shell using the reference app as the macOS-oriented baseline.

Add:

- `shell/index.ts`.
- `shell/src/ShellApp.tsx`.
- `shell/app.config.ts`.
- `shell/babel.config.js`.
- `shell/metro.config.js`.
- `shell/package.json`.

Validation:

```sh
cd shell && LEGEND_APP=music npx expo config --type public
```

### Phase 3: Apps

Create:

- `apps/music`.
- `apps/markdown`.

Music UI:

```tsx
export function App() {
  return <Text>Hello Music</Text>;
}
```

Markdown UI:

```tsx
export function App() {
  return <Text>Hello Markdown</Text>;
}
```

Validation:

```sh
bun run music macos
bun run markdown macos
```

### Phase 4: Native Module Package

Create `packages/music-test` as a New Architecture package with:

- TurboModule spec.
- Fabric/native UI component spec.
- iOS implementation.
- Android implementation.
- macOS implementation.
- Podspec and React Native config.

Add it only to the music manifest.

This is the highest-risk phase. The concept is supported by React Native New Architecture codegen and `react-native-macos` native module/component support, but the exact macOS codegen and pod integration should be validated before broadening the package. Keep the first native API deliberately minimal.

Validation:

```sh
bun run music macos
bun run verify music macos --includes @legend-apps/music-test
bun run verify markdown macos --excludes @legend-apps/music-test
```

### Phase 5: iOS and Android Prebuild

Wire Expo prebuild for `shell`.

Validation:

```sh
bun scripts/prebuild-app.ts music ios --clean
bun scripts/prebuild-app.ts music android --clean
bun scripts/prebuild-app.ts markdown ios --clean
bun scripts/prebuild-app.ts markdown android --clean
```

Then run:

```sh
bun run music ios
bun run markdown ios
bun run music android
bun run markdown android
```

### Phase 6: Release Builds

Add release build commands for all app/platform combinations.

Validation:

```sh
bun run build:all
```

### Phase 7: Verification Hardening

Make `verify-app.ts` deterministic enough to use as a regression guard.

Checks:

- Fail when `LEGEND_APP` is missing.
- Fail on stale generated config.
- Fail when app manifest references unknown packages.
- Fail when platform-specific native module lists include unsupported platforms.
- Fail when `markdown` includes any `music-test` path, symbol, or autolinking entry.

Validation:

```sh
bun run verify:all
```

## Open Decisions

- Whether to commit generated `shell/macos` immediately or regenerate it from a script. Initial recommendation: commit `shell/macos`, because Expo does not own macOS generation.
- Whether to commit generated `shell/ios` and `shell/android`. Initial recommendation: gitignore them and rely on Expo prebuild.
- Whether `packages/music-test` should be an Expo module, a pure React Native New Architecture module, or a hybrid. Initial recommendation: start as a React Native New Architecture package because the requested API is specifically TurboModule plus native UI component.
- Whether release builds should produce signed distributables in phase 1. Initial recommendation: build unsigned/local release artifacts first, then add signing as a separate plan.

## Definition of Done

- `bun run music macos` renders `Hello Music` and `Music Test Native`.
- `bun run markdown macos` renders `Hello Markdown`.
- `bun run music ios` and `bun run music android` can generate and run native projects through Expo prebuild.
- `bun run markdown ios` and `bun run markdown android` can generate and run native projects through Expo prebuild.
- `bun run music build <platform>` works for `macos`, `ios`, and `android`.
- `bun run markdown build <platform>` works for `macos`, `ios`, and `android`.
- `bun run verify markdown <platform> --excludes @legend-apps/music-test` proves markdown does not include `music-test`.
- `bun run verify music <platform> --includes @legend-apps/music-test` proves music does include `music-test`.
